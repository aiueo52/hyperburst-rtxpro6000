# 2026-11-12 experimental QSA relative prefill

The fork adds `SGLANG_QSA_RELATIVE_PREFILL`, an experimental setting that defaults to `0`.
Setting it to `1` opts into request-relative prefill logits with key splitting in the QSA
indexer; CUDA, TileLang and a positive host-derived width are required, otherwise the
existing path runs. It is not bit-exact and does not change decode speed. It is worth
trying only for contexts well above 100,000 tokens.

- Fork commits: `ce1c11faa` adds the setting to `qsa/mqa.py` and `qsa/qsa_indexer.py`,
  `cb1e6bff3` adds the documentation and a CPU test, and `8edd1fab4` records the operation
  check. The change is a backport of jpezzulli/sglang-rtxpro6000 commit
  `d4703ed417393655ad84b1062b474b674a238393` (Apache-2.0). It is not part of the numbered
  patch series in `patches/sglang/`.
- Measurements cover only `wa`, one stream, thinking off, on a pre-release tree with
  matching QSA files apart from the knob name and comment header. With 200,000 cached
  tokens, server-side prefill of 4,096 new tokens went from a median of 0.431 s to
  0.343 s (-20.3%, 6 measurements per arm). In a synthetic about-200,000-token lookup
  run of 600 questions per arm, the knob-off launches scored 536 and the knob-on
  launches 538.
- The speed and quality numbers have not been re-measured on the public tree, where a
  short operation check passed (53/60 vs 52/60 correct, knob 0 vs knob 1).
- Real documents, code or conversations, thinking mode, multi-step reasoning over long
  contexts, concurrency above 1 and other serve modes were not tested.
