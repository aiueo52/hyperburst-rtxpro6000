# 限界と注意

> 2026-11-12 に [README](../../README.ja.md) から移しました。文は変えていません。変えたのは見出しの段と相対リンクの向きだけです。

この節は過去の 9 月と 2026-10-02 の構成の説明であり、上の 4 件同時処理のフォークの説明ではありません。

- **公開していないもの:** 追加学習した先読み役(MTP ヘッド)と、非公開の候補単語の表は、作者の非公開の会話記録や
  作業記録から作ったため公開していません。当時の文章やエージェントの実行では、公開モデルそのままの先読み役は当たりが少なく、
  追加学習で速さが約 5〜10 % 上がりました。これは一般的な速さの保証ではありません。公開データだけで作った候補単語の表(`tokenmaps/public/`)は、非公開の表と 72.0 % の単語が
  共通です。元の先読み役とこの表を組み合わせて測ると(2026-10-06)、`wa` は非公開の組み合わせよりコード編集で約 20 %、
  文章とエージェントで 8〜15 % 遅くなりました(表は「2026-10 の更新」の節)。自分が使ってよい文章から作ることもできます(`tokenmaps/README.md`)。
  先読み役も自分のデータで学習し直せます(`docs/train-your-own-mtp-head.md`、英語)。
  公開データだけで学習し直す作り方と、1 回分の結果(重みは含まない)は `docs/public-data-mtp-head.md`(英語)にあります。
- **問題文の種類が少ない。** 見出しの表は各 1 問です。特にコード編集はほぼ同じ文字の繰り返しなので、
  先読みがとても当たりやすい(1 回で平均約 12 トークン確定)特殊な例です。8 問の表のほうが公平です。
- **計測のぶれ。** 同じ GPU で 4K・160 Hz の画面を表示していたため、画面描画が割り込み、1 回の計算が最大
  7.5 % 遅くなることを確認しました。同じ設定でも日や時間によって ±10〜15 % 変わったので、比較は同じ時間帯に行い、
  GPU の実際の計算時間や当たり数も別に測って判断しました(`docs/measurement.md`)。
- **省略(枝刈り)はモデルの計算を変えます。** 品質テストでは有意な差は見つかりませんでしたが、GSM8K と HumanEval の非劣性は
  確認できていません。また品質テストは「考える」モード OFF・最大 2 件同時で、速さの計測(1 件ずつ・ON)とは条件が
  違い、1 件ずつのときほど省略が多くなるため、厳しめの確認にはなっていません。省略するかどうかは答え合わせに並ぶ
  全トークンで決まるので、先読み役(学習した先読み役・候補の単語の絞り方・幅)を変えても本体の出力が変わり得ます。
  `PRUNE_TAU=0` で無効にできます。
- **毎回まったく同じ答えにはならない。** 一部の計算が足し算の順番に依存するため、greedy 設定でも少し変わります。
- **1 人で使う前提の設定です。** 複数の人が同時に使う場合の速さは最適化していません。また、既知の問題が 3 つあります
  (`docs/optimizations.md` の H7、英語)。2 つは同時に複数のリクエストを動かしたときや別のプログラムから呼んだときだけ、
  残る 1 つ(高速化の近似で、確率がまったく同じ候補が境目に多く並ぶまれな場合)は温度ありの 1 リクエストでも起こりえます。
- 出発点の数字だけ、ワークロード推奨の温度(0.2〜0.7)で計測しており、他は温度 0 です。
- **過去のテストの問題:** 不採用の `NGRAM_CHAIN` 先読み方式の単体テスト 2 つは、後のログ変更で失敗していました
  (`test_ngram_chain_worker.py`)。このテストファイルは 2026-10-27 の更新で削除しました。この先読み方式は、計測済み・既定の起動設定では使いませんが、`launch/serve-fast.sh` の実験用 `ngram` 設定では選択されます。
