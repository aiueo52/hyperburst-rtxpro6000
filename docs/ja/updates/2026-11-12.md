# 2026 年 11 月 12 日の実験中の QSA prefill の設定

フォークに `SGLANG_QSA_RELATIVE_PREFILL` を加えました。実験中の設定で、既定値は `0` です。
`1` にすると、入力を読む prefill の際、各行のキーの範囲を基準にスコアを置き、
キーを分けて計算します。CUDA と TileLang、CPU 側の長さから求めた正の幅が必要で、
そろわないときは今までの道で動きます。生成するトークンは無効時と完全には一致せず、
decode の速さは変わりません。試す価値があるのは、100,000 トークンを大きく超える入力だけです。

- フォークの commit: `ce1c11faa` が `qsa/mqa.py` と `qsa/qsa_indexer.py` に設定を加え、
  `cb1e6bff3` が文書と CPU のテストを加え、`8edd1fab4` が動作の確認を記録します。
  jpezzulli/sglang-rtxpro6000 の commit `d4703ed417393655ad84b1062b474b674a238393`
  (Apache-2.0)からの移植です。`patches/sglang/` の番号つきの patch には入っていません。
- 測ったのは `wa`、同時に 1 件、thinking 無効だけです。測定に使った公開前の木と
  今回の QSA ファイルは、設定名と先頭のコメント以外は同じです。200,000 トークンが
  キャッシュにある状態で、新しい 4,096 トークンを読むサーバー内の時間は、中央値で
  0.431 秒から 0.343 秒になりました(-20.3%、各 6 回)。約 200,000 トークンの合成の文章から
  1 件を探す問題(各 600 問)の正解は、無効時 536、有効時 538 でした。
- 速さと質の数字は、公開の木では測り直していません。公開の木では短い動作の確認だけを行い、
  通りました(60 問中の正解は無効時 53、有効時 52)。
- 実際の文書・コード・会話、thinking 有効、長い入力での何段かの推論、同時に 2 件以上、
  ほかの起動設定は確認していません。
